# Oceanseo 个人版与收费版域名、路由分离提案

状态：讨论稿，2026-10-12。未修改 DNS、线上 Caddy、服务、数据、客户端配置或公开下载。本地 `services/deployment/Caddyfile` 已成为个人专用模板，不能直接覆盖仍含商业旧路由的线上配置。

## 建议的产品边界

保留 `oceanseo.gellaronline.cc` 为开源个人版官网、说明和下载入口。收费产品使用 `app.oceanseo.gellaronline.cc`；其邀请内测使用 `preview.oceanseo.gellaronline.cc`。产品将来扩展手作领域时，`app` 不绑定拼豆这一项功能。若收费产品希望完全独立品牌，可以替换商业 hostname，个人版不用随之改名。

| 域名 | 路由 | 归属与用途 |
| --- | --- | --- |
| `oceanseo.gellaronline.cc` | `/`、`/downloads/*` | 个人版介绍、开源链接、个人安装包 |
| 同上 | `/docs/*` | 建议增加的个人版文档；目前不是已上线能力 |
| 同上 | `/v2/*`、`/v1/vault` | 保留既有个人账号和兼容同步契约 |
| 同上 | `/manage/` | 如发布个人管理界面，仅用于个人服务的邀请、角色和权限 |
| `app.oceanseo.gellaronline.cc` | `/` | 收费产品正式 Web/PWA；需要商业仓库改 Vite base 后构建 |
| 同上 | `/v2/*`、`/v3/*` | 商业账号及商业资料 API，反代至商业正式服务 |
| 同上 | `/manage/` | 商业正式管理入口，由商业服务核验管理权限 |
| `preview.oceanseo.gellaronline.cc` | `/`、`/v2/*`、`/v3/*`、`/manage/` | 独立的商业内测客户端、API 和管理界面 |

优先让各客户端与自己的 API 同源，减少跨域、CSP 和鉴权配置成本。暂时没有必要额外拆 `api` 或 `admin` 域名。管理界面可用同源路径；隐藏路径或 noindex 都不能代替服务端权限检查。

个人版的官网可有一个明确标注「收费产品」的外链；商业官网可链接「开源个人版」。两者不共用登录入口、任务资料或会员权益。个人工具不因商业付费而被锁定。收费项目目前仍属邀请内测，域名分离不代表支付、订阅或正式发行已经完成。

## 现有路径与兼容约束

拆分前配置把个人官网、下载、`/v2` 账号、`/v1/vault` 同步，以及商业 `/app/`、`/preview/*`、`/preview/manage/` 放在同一 hostname。本次依据原配置和商业交接文档整理，没有重新核验线上状态。

个人原生客户端已内置主域名，继续保留该 endpoint 和原 API 路径，避免要求用户为网站改版重新连接资料库。收费旧 Web/Android 使用的 `/preview/v2` 和 `/preview/v3` 也应在迁移期反代到**原商业内测服务**，保留方法、Authorization、正文及原资料根；不能将其导向个人账号服务。API 不用普通 301/302 跨域跳转。

旧商业 `/app/` 是已使用的 PWA 路径。需要保留旧 `sw.js`、manifest、资源路径及 SPA 深链一段时间：先让新 hostname 的商业入口运行并提供迁移说明，再处理旧 HTML 入口的跳转。不要把所有 `/app/*` 一次性跳转，导致旧 service worker 或离线资源失效。新 origin 的缓存、离线队列和登录不会自动迁移；服务端已确认资料可以重新登录后取得，旧设备未上传队列必须先同步或导出，禁止把旧缓存静默清空。

新商业客户端 endpoint 需要显式指向对应正式/内测 hostname；Vite base、manifest 的 start_url/scope、service worker scope、CSP、登录缓存键和 Android 发布配置一并验证。最初可以在新 hostname 保持 `/app/` 与 `/preview` 前缀，完成 host 迁移后再收敛为表中的路径，减少一次切换的变量。

## 运维与数据归属

个人、商业正式、商业内测分别拥有独立的 systemd 服务、源码目录、数据库根、备份/恢复目录、会话与密钥。各仓库发布自己的静态目录与服务，反向代理由统一的站点配置管理，不能让任何单个应用的部署脚本覆盖另一应用的站点。

收费版不复用个人 `4791` 账号或 `4789` vault 作为正式数据源。已有商业 `/var/lib/oceanseo-preview` 保持原来源；商业新环境需要独立初始化或经验证的备份恢复，不连接个人数据库，不通过复制浏览器 token 实现共享登录。若将来需要统一账号，应另行设计身份提供方与跨产品授权。

上线顺序：确认商业 hostname 与正式/内测数据归属 → 新域名 DNS/TLS 与反代 → 商业仓库发布新 origin 的客户端并验证登录/保存/接续/导出 → 保留旧 API 兼容反代与 PWA 迁移说明 → 观察旧客户端使用情况后收尾。每步保留原配置、静态版本和服务根用于回退。

本轮仅讨论分工和路径。后续部署须结合服务器实际配置制定具体变更，单独验证旧客户端、跨设备资料、离线未同步内容和回退。
